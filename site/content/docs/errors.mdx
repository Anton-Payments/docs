Every non-2xx response from `/v1` has the same JSON shape, whatever the status. Branch on `error.code`, not on `error.message`: messages are written for people and can change, codes are a stable contract.

## The error object

```json
{
  "error": {
    "type": "invalid_request_error",
    "code": "amount_precision_invalid",
    "message": "CAD amounts allow 2 decimal places; got 3.",
    "param": "amount",
    "doc_url": "https://docs.antonpayments.com/api-reference/errors#amount_precision_invalid",
    "request_id": "req_01JD3XB7Q2"
  }
}
```

| Field | Type | Always present | Description |
| --- | --- | --- | --- |
| `error.type` | string | Yes | The broad class of error. It follows the HTTP status. See [Types](#types). |
| `error.code` | string | Yes | Stable, machine-readable, snake_case. Every code is listed in the [catalog](#error-codes) below, under an anchor with the code's name. |
| `error.message` | string | Yes | A description for a developer. Safe to log. It never contains personal data. A `5xx` message is always generic. |
| `error.param` | string | No | The request field or query parameter at fault, when there is one (`amount`, `individual.birth_date`). |
| `error.doc_url` | string | Yes | A link to this page at the code's anchor. |
| `error.request_id` | string | Yes | Our identifier for the request (`req_...`). The same value is in the `Request-Id` response header. Quote it in support requests. |
| `error.details` | array | No | Present on validation failures. One entry per failing field, so you can fix a whole form in one pass. |

## Validation errors

A request that is well formed but fails field validation returns `422` with `code: "validation_error"` (or a more specific code) and a `details` array. Each entry has the failing `param`, a `code` and a `message`.

```json
{
  "error": {
    "type": "invalid_request_error",
    "code": "validation_error",
    "message": "validation failed",
    "doc_url": "https://docs.antonpayments.com/api-reference/errors#validation_error",
    "request_id": "req_01JD3XB7Q2",
    "details": [
      { "param": "individual.first_name", "code": "validation_error", "message": "is required" },
      { "param": "destination_currency", "code": "validation_error", "message": "is required" },
      { "param": "individual.birth_date", "code": "validation_error", "message": "must be YYYY-MM-DD" }
    ]
  }
}
```

`param` uses dotted paths for nested objects (`individual.address.country`). Fix every entry before you retry.

## Types

The type follows the status, so you can handle a class of error without knowing every code.

| Type | Status | Meaning |
| --- | --- | --- |
| `authentication_error` | 401 | No credentials, or credentials that do not verify. |
| `permission_error` | 403 | Valid credentials that lack the permission, scope or capability. |
| `invalid_request_error` | 400, 404, 405, 409, 410, 413, 422 | The request cannot be completed as sent: malformed (400), no such resource (404), wrong method (405), conflicts with current state (409), retired endpoint (410), too large (413), or fails a business rule (422). |
| `idempotency_error` | 409, 422 | An `Idempotency-Key` problem: still in flight (409) or reused with a different body (422). A missing key is a `400 invalid_request_error` with the code `missing_idempotency_key`. |
| `rate_limit_error` | 429 | You are over a rate limit. |
| `api_error` | 500, 502, 503 | Something failed on our side or at a provider. Retrying with the same `Idempotency-Key` is safe. |

## Statuses

| Status | When |
| --- | --- |
| `200` | Success: read, update, state change. A delete returns the deleted object's `id`, its `object` name and `"deleted": true`. |
| `201` | A new resource was created. |
| `202` | Accepted for asynchronous work. The body is the resource in its pending state. |
| `400` | The request is malformed: JSON, an unknown field or parameter, a type, an ID's shape, a body that is not `application/json` (`invalid_content_type`), a missing `Idempotency-Key`. |
| `401` | No credentials, or credentials that do not verify. Carries `WWW-Authenticate`, see [Authentication challenge](#authentication-challenge). |
| `403` | Valid credentials without the permission, scope or capability. |
| `404` | The resource does not exist for your account. |
| `409` | The request conflicts with the resource's current state, or an identical request is still in flight. |
| `413` | The body or upload is larger than the endpoint accepts. |
| `422` | The request is well formed but fails a business rule. |
| `429` | Rate limited. Carries `Retry-After`. |
| `500`, `502`, `503` | Our failure, a provider's failure, or temporary unavailability. A `503` carries `Retry-After`. |

## Authentication challenge

Every `401` carries a `WWW-Authenticate` header (RFC 6750, RFC 9449). It names the scheme, the realm and the DPoP proof algorithms the API accepts:

```
WWW-Authenticate: DPoP realm="anton", algs="ES256 EdDSA"
```

When you sent a credential and it was refused, the header also names the reason: `error="invalid_token"` for an access token (or a static API key) that does not verify, and `error="invalid_dpop_proof"` when the DPoP proof is what failed. A request with no credential carries no `error`. `POST /oauth/token` answers a `401` with `WWW-Authenticate: Basic realm="anton"` and keeps its RFC 6749 body.

## Handling errors

- **`4xx`**: do not retry unchanged. Fix the request (the exceptions are `409 idempotency_in_flight` and `429`, below).
- **`409 idempotency_in_flight`**: wait a moment and send the same request again. The completed response is replayed.
- **`429`**: wait the number of seconds in `Retry-After`. See [Rate limits](/concepts/rate-limits).
- **`5xx`**: retry with the same `Idempotency-Key` and exponential backoff with jitter. If it persists, send us the `request_id`.
- Treat a `code` you do not recognise as the generic case for its `type`. New codes can be added at any time. See the [changelog](/changelog).

`POST /oauth/token` is the one exception to this format. It follows RFC 6749 (`{"error": "invalid_client", "error_description": "..."}`) because OAuth libraries expect it. See [Authentication](/authentication#mint-a-token).
