<Notes>

It describes the full `/v1` surface: authentication, beneficiaries and instruments, payouts and batches, balances and accounts, FX, webhooks, verifications and Anton Intelligence. Download the [OpenAPI description](/openapi-merchant.yaml) to generate a client or import the API into a tool such as Postman.

### Versioning

- Versions are dates. Your account is pinned to the latest version when you create your first OAuth client. Every response carries an `Anton-Version` header, and you can send `Anton-Version` on a single request to try another version.
- A breaking change ships only as a new version, so an integration keeps working unchanged. New routes, optional fields, enum values, error codes, event types and headers can appear in any version.

### What every resource looks like

- Every object has `id`, `object`, `livemode`, `created_at` and `updated_at`. Objects you create also carry `metadata`, including batches, beneficiary imports and verifications. Send it on a batch upload or a beneficiary import as a `metadata` form field holding a JSON object string.
- Amounts are decimal strings with a currency, always rendered at the currency's precision. `GET /v1/currencies` lists each currency's precision.
- Timestamps are RFC 3339 in UTC with milliseconds, for example `2026-12-01T14:03:22.104Z`. A timestamp filter accepts only that form, such as `created_after=2026-11-01T00:00:00.000Z`; any other form is a `400`.
- A single resource is returned at the top level, with no `data` wrapper. A payout is the same object whether you read it or receive it in a webhook, and `risk`, `delivery` and `session_quality` are always present (`null` when empty).
- Both sides of a conversion are `source_*` and `destination_*`, in payouts, pricing and FX.
- Lists are `{"object": "list", "data": [...], "has_more": ..., "next_cursor": ...}`, with `limit` from 1 to 100 (default 25), `created_after` and `created_before`, newest first.

### Requests and responses

- A request with a body must be `application/json` (an upload takes `multipart/form-data`), otherwise `400 invalid_content_type`.
- Unknown fields, unknown query parameters and wrong types are rejected with `400`. A path ID with the wrong prefix or shape is `400 resource_id_invalid`, with `param` set; a well-formed ID that does not exist for your account, or belongs to another account, is `404 resource_missing`. A bad or expired `cursor` is `400 cursor_invalid`.
- Partial updates use `PATCH`. In a `PATCH`, `null` clears a field and a field you leave out is not changed. Deletes return the object's `id`, `object` and `"deleted": true`.
- Creates return `201`. Work that finishes later returns `202` with the resource in its pending state.
- Every `POST` that creates or changes something requires an `Idempotency-Key`. Keys last 24 hours. Reusing a key with a different body is `422 idempotency_key_reused`, and a request still in flight is `409 idempotency_in_flight`. A replay is marked `Idempotent-Replayed: true`. Secrets are never replayed. `PATCH` and `DELETE` accept an `Idempotency-Key` but do not require one, and `POST /v1/intelligence/evaluations/validate`, which stores nothing, does not need one.
- Every response carries an `Anton-Version` header, including a `401`. A `429` and a `503` carry `Retry-After`.
- Field names are consistent across resources: an instrument's flag is `default`, an owner's share is `ownership_percentage`, and a batch's rate time is `rate_at`.
- A beneficiary's date of birth is `birth_date`.
- Quotes are created at `POST /v1/fx/quotes` and `POST /v1/pricing/quotes`.
- Fields appear in a fixed order: `id`, `object`, `livemode`, `status`, the resource's own fields, `metadata`, `created_at`, `updated_at`.
- `GET /v1/accounts/{currency}/transactions` is gone. Use `GET /v1/transactions?currency=`.
- Every response carries a `Request-Id` header (`req_...`). You can send your own identifier as `X-Client-Request-Id`; we log it beside ours.

### Errors

- A zero or negative amount is `422 amount_invalid`, with `param` naming the field. An amount that is not a decimal string is `400 type_mismatch`.
- Sending a test event to an inactive webhook subscription is `409 webhook_subscription_inactive`, and an action a verification's state does not allow is `409 invalid_verification_state`.
- Every error has `type`, `code`, `message`, `doc_url` and `request_id`, and `param` and `details` where they apply. `type` follows the status. Every code is listed on the [errors page](/errors).
- Every `401` carries a `WWW-Authenticate` header naming the DPoP scheme and the accepted proof algorithms, and the reason when a credential was refused. See [authentication challenge](/errors#authentication-challenge).

### Webhooks

- Events are `{id, object: "event", type, api_version, livemode, created_at, data: {object}}`. `data.object` is the same resource the API returns. A retried delivery is identical to the first. See [webhook events](/concepts/webhook-events).
- A signing secret is shown once, when you create a subscription or rotate it. Rotating keeps the previous secret signing for 24 hours. See [webhook signing](/concepts/webhook-signing).

### Sandbox

- `POST /v1/sandbox/deposits` credits a sandbox balance so you can run a payout end to end from the API. See [sandbox test data](/sandbox/test-data).

### Moving from the pre-release API

If you built against earlier documentation:

- `dest_*` fields are `destination_*`, FX `sell_*` and `buy_*` fields are `source_*` and `destination_*`, and `fixed_dest` is `fixed_destination`.
- `PUT` updates are `PATCH`. `POST /v1/fx/exchange` is `POST /v1/fx/exchanges`.
- The error envelope is the object described above, replacing `{message, code}`. Business-rule failures are `422`, state conflicts are `409`, and reusing an idempotency key with a different body is `422 idempotency_key_reused`.
- A webhook signing secret can no longer be read back; rotate to get a new one.
- Static API keys are not accepted; use OAuth client credentials with DPoP.

</Notes>

<Entry date="2026-10-21" title="Transactions: direction, filters, single reads and export" tags="Added,Changed"
  lede="Every movement now says which way it went and what caused it, and the whole ledger exports as CSV."
  action="If you held a transactions cursor from before this release, start again from the first page.">

<Endpoints items={[["GET", "/v1/transactions/{id}", "One movement"], ["GET", "/v1/transactions/export", "The ledger as CSV, audited"], ["GET", "/v1/fx/exchanges/{id}", "An exchange with its markup and fee"]]} />

<Notes>

### Added

- **`direction` on transactions.** `credit` for money in, `debit` for money out. Amounts stay unsigned. It's absent on the rare transaction whose side can't be told.
- **`payout_id` and `exchange_id` on transactions**, linking a movement to the payout or FX exchange it belongs to, when known.
- **Filters on `GET /v1/transactions`**: `type`, `direction`, `status`, `currency`, `created_after`, `created_before`.
- **`GET /v1/transactions/{id}`** and **`GET /v1/fx/exchanges/{id}`** (the exchange with its quote's markup and fee).
- **`GET /v1/transactions/export`**: the matching transactions as CSV. It needs the report-download permission, and each export is audited.
- **`return` transaction type**, for a payout returned to your balance or a deposit recalled from it.

### Changed

- **Transaction `type` and `status` values** are now always lowercase and from a fixed list: types `payin`, `payout`, `fee`, `exchange`, `transfer`, `return`; statuses `completed`, `pending`, `failed`, `returned`. The values previously documented (`credit`, `debit`, `fx`, `posted`) were never sent.
- **Unknown filter values are rejected** with `400 invalid_request` instead of being ignored.
- **Transaction list cursors.** Pages no longer repeat or skip a transaction that arrives while you page. A cursor issued before this change returns `400 cursor_invalid`; start again from the first page.
- **`GET /v1/fx/exchanges` filters** are documented as what the API accepts: `status` and `currency`.

</Notes>

<Entry date="2026-09-24" title="Payout holds, cannot_be_processed, and RFI responses" tags="Added,Changed,Deprecated"
  lede="A payout under review now says so, and can't be cancelled until the review ends. A payout that can't be processed fails with its own code."
  action="Treat a held payout as waiting, not failed, and stop cancelling it while it's held.">

<Codes items={[["409", "payout_on_hold", "Cancelling a payout under review"]]} />

<Notes>

### Added

- **`on_hold` payout status.** A payout that waits on a review reads `status: "on_hold"`. It carries no reason. See [How Anton Evaluates Payouts](/concepts/how-anton-evaluates-payouts).
- **`cannot_be_processed` payout failure.** A payout that cannot be processed fails with `failure_code` `cannot_be_processed`. It is final and cannot be cancelled via the API.
- **`409 payout_on_hold`** on `POST /v1/payouts/{id}/cancel` when the payout is under review, whatever the review is about. See [Errors](/errors).

### Changed

- **Cancellable statuses.** A payout under review (`status: "on_hold"`) can no longer be cancelled until the review concludes.
- **RFI responses.** Responding to an RFI, and attaching documents to a response, now requires the `rfis.respond` permission, held by the Admin and Operator roles, in the dashboard. Operators can now respond. API credentials cannot respond to RFIs.
- **Batch validation.** Validation no longer returns screening results. The warning `type` values are now documented, and `beneficiary_name_change` warnings name the changed field instead of the beneficiary's name.
- **Blocked beneficiaries.** Documentation now describes `blocked` as "cannot be used for payouts".

### Deprecated

- **`screening.hit` is no longer sent.** A payout under review shows `status: "on_hold"` instead. Existing subscriptions keep working but receive no deliveries.

</Notes>

</Entry>

<Entry date="2026-07-17" title="Machine credentials across the payout surface" tags="Added,Changed"
  lede="A credential with the payouts scope can now do everything a payout integration needs, end to end. Reading a payee's personal details stays with people in the dashboard.">

<Endpoints caption="Open to a payouts-scoped credential" items={[["POST", "/v1/payouts"], ["POST", "/v1/payouts/{id}/cancel"], ["POST", "/v1/beneficiaries"], ["POST", "/v1/fx/exchanges"], ["POST", "/v1/webhooks"]]} />

<Notes>

OAuth+DPoP credentials carrying the `payouts` scope can now do everything a payout integration needs. Before, machine callers could read but not change data on several payout endpoints; credential scopes now map directly to the permissions each endpoint requires, so a `payouts`-scoped credential creates and cancels payouts, manages beneficiaries and instruments, uploads and confirms batches, executes FX, and manages webhook subscriptions.

### Added

- **Scope-mapped permissions for machine credentials.** Each credential scope carries a fixed permission set enforced per endpoint. `payouts` covers the money-movement surface; `intelligence` covers evaluations and Verifications; both cover webhook subscription management.

### Changed

- **Beneficiary PII is write-only for machine credentials.** `PATCH /v1/beneficiaries/{id}/pii` is available (your system is the source of the data); `GET /v1/beneficiaries/{id}/pii` answers `403` to a machine credential. Reading personal data back (payee PII, verification names, captured documents) is for signed-in admin users of the merchant dashboard, audit-logged per access. A leaked API credential cannot harvest identities.
- **Approval decisions stay human.** Payout approve/reject (maker-checker) rejects machine credentials. An approver must be a signed-in portal user other than the creator.
- **Access tokens without a `scope` claim now grant nothing.** The transitional full-scope default for pre-scope-era tokens has been removed; every legitimately minted token has carried the claim since it shipped, and a claim-less token now fails closed.

</Notes>

</Entry>

<Entry date="2026-07-16" title="Verifications API" tags="Added"
  lede="Identity checks for your own customers, hosted by Anton and sanctions-screened when they finish. What used to be dashboard-only is now an API.">

<Endpoints items={[["POST", "/v1/verification-subjects", "Start a verification"], ["GET", "/v1/verification-stats", "Where your customers drop off"]]} />

<Notes>

Additive, non-breaking. The verification module, previously reachable only through the merchant dashboard, is now part of the public API for OAuth+DPoP credentials carrying the `intelligence` scope.

### Added

- **Verifications API.** Identity checks for people and businesses, through hosted flows: create verification subjects (`POST /v1/verification-subjects`), list and read them, re-verify, resend / regenerate / revoke links, resend per-owner (UBO) links, and read funnel stats (`GET /v1/verification-stats`). Every completed verification is sanctions-screened through Anton Intelligence, with the backing `evaluation_id` on the attempt's `screening` block. See the [Verifications guide](/concepts/verifications).
- **`verification.*` webhook events.** `verification.link_sent`, `verification.started`, `verification.approved`, `verification.declined`, `verification.review`, and `verification.expired` are documented in the [event catalog](/concepts/webhook-events#verification). `link_sent` fires as the delivery receipt for Anton-delivered hosted links.

### Security

- **PII-free machine surface.** Subject and owner names are masked on every API read; the audited name-reveal and captured-document viewing remain dashboard-only (admin, per-access audit trail). Hosted links are secret-once: returned only by the response that minted them.

</Notes>

</Entry>

<Entry date="2026-06-10" title="Capabilities, AI-Compliance tier, authenticated Intelligence" tags="Added,Changed"
  lede="What an account can do and what a credential may do are now two separate things, and Intelligence runs under your own credentials.">

<Codes items={[["403", "capability_required", "The account lacks the capability"], ["403", "insufficient_scope", "The credential lacks the scope"], ["409", "idempotency_in_flight", "The first attempt is still running"]]} />

<Notes>

Additive, non-breaking changes to the v1 contract. Existing integrations are unaffected: every existing account keeps both capabilities, and every existing credential behaves as full-scope.

### Added

- **Account capabilities and credential scopes.** Every merchant account carries a capability set (`payouts`, `intelligence`); every OAuth client carries a scope set fixed at creation and embedded in access tokens as a `scope` claim (echoed in the token response). Effective access is `scopes ∩ capabilities`. See [Capabilities & Scopes](/concepts/capabilities).
- **AI-Compliance-only tier.** Accounts can be provisioned with the `intelligence` capability only, with full access to Anton Intelligence, dashboards, webhooks and credential management. Every payout endpoint is refused for these accounts (`403 capability_required`).
- **Authenticated Intelligence API.** `POST /v1/intelligence/evaluations` (with required `Idempotency-Key`), `GET /v1/intelligence/evaluations` (new, cursor-paginated), `GET /v1/intelligence/evaluations/{id}`, and `POST /v1/intelligence/evaluations/validate` now run under merchant credentials with the `intelligence` scope. Evaluations persist under your account and reads are strictly merchant-scoped.
- **New error codes.** `403 capability_required`, `403 insufficient_scope`, `409 idempotency_in_flight`, `503 idempotency_unavailable` are now documented across the [error catalog](/errors).

### Changed

- **`X-RateLimit-*` headers documented in the OpenAPI spec.** `X-RateLimit-Limit` / `-Remaining` / `-Reset` (present on every response since v1.0.0) are now part of the published spec on the `429` response.
- **OpenAPI 3.1 hygiene.** Nullable fields now use `type: [string, "null"]` per OpenAPI 3.1; the spec lints clean.

</Notes>

</Entry>

<Entry date="2026-04-18" title="v1.0.0" tags="Added,Changed" feature
  lede="The merchant contract froze. Amounts became decimal strings, every list moved to cursors, and a price could be pinned before a payout.">

<Diff caption="Two habits it changed" lines={["- GET /v1/payouts?offset=50", "+ GET /v1/payouts?limit=25&cursor=<next_cursor>", "- 1234.5", "+ \"1234.50\""]} />

<Notes>

The v1.0.0 merchant contract is now frozen. Merchant integrations built against this surface will not break in minor or patch releases.

### Added

- **Bindable pricing quotes.** `POST /v1/pricing/quotes` now returns `quote_id` (prefix `pq_`) and `expires_at`. Pass `quote_id` on `POST /v1/payouts` to lock the quoted fee. Missing or mismatched quotes surface as `422 quote_expired` / `422 quote_already_used` / `422 quote_mismatch`.
- **Per-merchant rate limits.** The base quota is per **merchant** (not per IP), so multi-seat merchants behind shared egress NATs get coherent quota accounting. See [rate limits](/concepts/rate-limits).

### Changed

- **Cursor pagination everywhere.** Every list endpoint uses `limit` + opaque `cursor` with `{ data, has_more, next_cursor }`. Legacy `offset` pagination has been removed.
- **Monetary amounts are decimal strings, scaled per currency.** Amount fields are always emitted at the currency's canonical scale (USD/EUR at 2 decimals, JPY at 0, BHD at 3, BTC at 8, USDC at 6). Never parse as a float.
- **ID prefix scheme normalised.** `pay_*` (payouts), `ben_*` (beneficiaries), `ins_*` (instruments), `bat_*` (batches), `whk_*` (webhook subscriptions), `evt_*` (events), `dlv_*` (deliveries), `pq_*` (pricing quotes), `fxq_*` (FX quotes), `fxx_*` (FX exchanges), `mer_*` (merchant). 
- **Corridor responses no longer expose `provider`.** Anton's rail graph is a commercial secret; the merchant view emits only the merchant-observable fields.
- **Timestamps are RFC 3339, in UTC.**
- **Webhook secret rotation.** `POST /v1/webhooks/{id}/secret/rotate` returns a fresh raw secret **exactly once**. The secret cannot be read back afterwards. Webhook creates also echo the raw secret once in the create response.
- **Idempotency scoping.** `Idempotency-Key` is scoped per `(merchant, path, body)`, so two merchants can never collide. Replays of identical bodies return the original response; replays with a different body return `422 idempotency_key_reused`.

### Security

- **Cross-merchant policy.** The merchant API never exposes counts, identities, or adverse-event signals derived from other merchants' activity, not even as booleans. Signals from across the network reach you only inside verification results, in the same form as results from outside providers.
- **PII isolation.** All beneficiary PII and payment instrument details are tokenized in a secure vault. Raw values are returned only to signed-in admin users of the merchant dashboard.

</Notes>
