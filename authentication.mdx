---
title: "Authentication"
description: "Anton authenticates API calls with per-merchant API keys. Keys are scoped to a single environment and carry full merchant privileges — treat them as bearer credentials."
---

Every request to the Anton Payments API requires an `Authorization` header carrying a bearer credential. The merchant surface accepts **two credential types on the same routes**:

- **API keys** (`ak_live_*` / `ak_test_*`) — for server-to-server integrations.
- **WorkOS portal JWTs** — issued to users signed in to the merchant dashboard. JWTs carry the authenticated user plus their merchant org and role.

Both are presented the same way:

```http
Authorization: Bearer ak_live_kS2f...
Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6...
```

This **dual-auth** model means an endpoint like `POST /v1/payouts` works identically whether it's hit by a headless job using an API key or by a merchant user driving the dashboard. API keys carry full merchant scope for the endpoints documented here; dashboard users are subject to the role model configured in your organization.

Requests without a valid credential return `401 Unauthorized`. API keys used against the wrong environment return `401` with `code: "key_environment_mismatch"`.

## Key formats

| Prefix | Environment | Base URL |
|---|---|---|
| `ak_live_` | Production | `https://api.antonpayments.com` |
| `ak_test_` | Sandbox | `https://api.antonpayments.dev` |

A test key will be rejected in production. A live key will be rejected in sandbox. A leaked key only exposes one environment's data.

## Using a key

<CodeGroup>

```bash cURL
curl https://api.antonpayments.dev/v1/beneficiaries \
  -H "Authorization: Bearer ak_test_kS2f..."
```

```javascript JavaScript
const response = await fetch("https://api.antonpayments.dev/v1/beneficiaries", {
  headers: {
    Authorization: `Bearer ${process.env.ANTON_API_KEY}`,
  },
});
const data = await response.json();
```

```php PHP
$ch = curl_init("https://api.antonpayments.dev/v1/beneficiaries");
curl_setopt($ch, CURLOPT_RETURNTRANSFER, true);
curl_setopt($ch, CURLOPT_HTTPHEADER, [
    "Authorization: Bearer " . getenv("ANTON_API_KEY"),
]);
$response = curl_exec($ch);
curl_close($ch);
```

```go Go
req, _ := http.NewRequest("GET", "https://api.antonpayments.dev/v1/beneficiaries", nil)
req.Header.Set("Authorization", "Bearer "+os.Getenv("ANTON_API_KEY"))
resp, err := http.DefaultClient.Do(req)
```

</CodeGroup>

## Creating and rotating keys

API keys are created and managed in the [merchant dashboard](https://app.antonpayments.com). Keys are only shown once at creation — store them in your secrets manager immediately. Anton does not retain the plaintext and cannot recover a lost key.

To rotate:

<Steps>
  <Step title="Create a new key">
    Generate a new key in the dashboard. Label it with the service or environment that will use it.
  </Step>
  <Step title="Deploy the new key">
    Update your secrets store and roll out the new key. Verify traffic is flowing against it.
  </Step>
  <Step title="Revoke the old key">
    Only after the new key is serving all traffic, revoke the old one from the dashboard. Revocation is immediate and cannot be undone.
  </Step>
</Steps>

## If a key is exposed

Revoke it immediately from the dashboard, then review recent activity in the dashboard's audit log for anything unexpected. Contact [help.antonpayments.com](https://help.antonpayments.com) if the leaked key belonged to production.

## Requirements

- **Use HTTPS.** Anton only accepts TLS 1.2+ connections. Plaintext requests are dropped at the edge.
- **Never commit keys to source control.** Use environment variables or a dedicated secrets manager.
- **Never include keys in frontend code.** All API calls must originate from a trusted backend.
- **Prefer one key per service.** Narrower blast radius when a key needs to be rotated.
